## 一句话项目介绍

> **GeoCiteOps 是一套"监测 + 优化 + 结构化"三位一体的 GEO 系统，帮品牌追踪和提升在 DeepSeek、豆包、通义千问、文心一言、ChatGPT Search、Perplexity、Gemini、Claude 等 8 大 AI 引擎中的被引用率。**

如果说 **SEO 优化的是"网页在百度/Google 的排名"**，那么 **GEO 优化的是"内容被 AI 引用的概率"**——这是 AI 搜索时代全新且快速增长的流量入口。

---

## 项目缘起：来自真实的内部需求

GeoCiteOps 最初是为姐妹项目 **[ZoomerAI](https://gitee.com/lethe_1/zoomer-ai-base)**（`zoomer-ai-base`）开发的，并不是凭空想象的练手项目。

### ZoomerAI 是什么

**ZoomerAI** 是一款基于 **Nuxt 4 + Vue 3** 构建的**多租户 AI 图像生成平台**——**已上线运营，并有大量付费用户在使用**：

- 🎨 **画布式编辑器**：基于 Konva.js 的可视化图层编辑
- 🤖 **ComfyUI 工作流集成**：一键 AI 图像生成
- 💬 **实时聊天**：WebSocket 驱动的协作
- 🏢 **多租户 SaaS 架构**：WebSite / User / Project 三级隔离，支持自定义域名、品牌 privatization
- 🔐 **JWT 鉴权 + RBAC**：SUPER_ADMIN / ADMIN / MEMBER 三级权限
- 💰 **已商业化**：真实付费用户在持续使用，是经过市场验证的生产级 SaaS 产品

### 为什么 ZoomerAI 需要 GEO

> "我们的 AI 图像平台已经有大量付费用户，但当新用户在 AI 搜索里问'AI 图像生成工具推荐'时，被引用的总是别人——我们流失的是真实的潜在付费用户。"

ZoomerAI 是**典型的会被 AI 搜索推荐的品牌型产品**——而它面临的问题，正是所有 AI 产品在 AI 搜索时代共同面临的：**产品再好，没被 AI 引用就等于在 AI 时代不存在**。对 ZoomerAI 这样的付费产品来说，**AI 引用率直接等同于获客成本和收入**。

### 从内部工具到开源项目

为了解决 ZoomerAI 的 AI 可见度问题，我们构建了 GeoCiteOps。在打磨过程中我们发现：

- **这是一个普遍痛点**：不只是 ZoomerAI，所有 SaaS / 品牌方都需要
- **市面上没有可用方案**：尤其是**跨国内外 8 大 AI 平台**的监测+优化
- **这是 AI 时代的 SEO**：一个正在打开的千亿级新赛道

于是我们把 GeoCiteOps **独立开源**（MIT 协议），让任何品牌都能用它提升 AI 引用率。**ZoomerAI 是它的第一个真实用户——一个有大量付费用户的生产级 SaaS，也是 GEO 价值最硬的验证场景。**

> 💡 **路演要点**：GeoCiteOps 不是为比赛而造的 Demo。它源自一个**已上线、有大量付费用户**的真实产品（ZoomerAI）的真实痛点，已在真实商业环境中验证，现开源给所有品牌方。**真实需求 + 商业验证 + 可复用**——这是绝大多数 Hackathon 项目不具备的稀缺组合。

## 一、为什么做这个：踩在 AI 时代的新赛道上

### 1.1 流量入口正在迁移

| 时代            | 用户行为                   | 优化对象         | 谁在赢                      |
| ------------- | ---------------------- | ------------ | ------------------------ |
| **搜索时代**      | 打开百度/Google，看 10 条蓝色链接 | SEO：网页排名     | SEO 工具厂商（Ahrefs、Semrush） |
| **AI 时代（现在）** | 直接问 AI，看一段答案 + 引用来源    | **GEO：被引用率** | **赛道空白，机会窗口期**           |

当用户问 AI"推荐一款好用的 AI 协作工具"时，**被 AI 引用的那个品牌赢了，没被引用的等于不存在**。

### 1.2 真实的痛点

- 品牌方完全不知道自己在 AI 答案里**排第几、有没有被提及、被谁引用**。
- AI 偏好引用的内容形态（数据锚点、定义句、结构化标记）和传统 SEO 内容**完全不同**，旧内容需要重写。
- 没有任何工具能**跨多个国内外 AI 平台**做监测和优化——这是市场空白。

### 1.3 这是可验证的机会

GEO 概念已有顶会学术论文背书（*GEO: Generative Engine Optimization*, arxiv 2311.09735，是**唯一**做了 A/B 实验的研究），但**尚无成熟开源实现**。GeoCiteOps 在抢占这个先发窗口。

## 二、做了什么：四大核心模块，已全部跑通

```
┌──────────────────────────────────────────────────────┐
│  Web 控制台 (Vue 3 + Naive UI)   ← 现场可演示          │
│  仪表盘 · 查询库 · 引用报告 · 内容优化 · Schema · 知识图谱│
├──────────────────────────────────────────────────────┤
│  API 网关  (Fastify + tRPC)                           │
├──────────────────────────────────────────────────────┤
│  四大核心模块                                          │
│  ① 引用监测   ② 内容优化   ③ Schema 生成   ④ 知识图谱   │
├──────────────────────────────────────────────────────┤
│  PostgreSQL + pgvector + 进程内向量库 (Zvec)          │
└──────────────────────────────────────────────────────┘
```

### 模块 ①：引用监测（Citation Monitor）— 跨 8 大 AI 引擎

模拟真实用户向 8 个 AI 平台提问，分析回答中：

- 品牌是否被**提及**（mention）
- 品牌是否被**引用为来源**（citation）
- 在答案中的**排名位置**（rank）
- 计算 **SOV（Share of Voice，声音份额）** = 品牌提及次数 / 所有品牌提及总次数

**覆盖的平台**（国内外全覆盖，这是竞品做不到的）：

| 国内                                  | 国外                                                |
| ----------------------------------- | ------------------------------------------------- |
| DeepSeek、豆包（火山引擎）、通义千问（阿里）、文心一言（百度） | ChatGPT Search、Perplexity、Gemini、Anthropic/Claude |

> ✅ **现场演示点**：输入一个查询 → 一键跨 8 个平台监测 → 看 SOV 分数和竞品对比。

### 模块 ②：内容优化器（Content Optimizer）— 把内容改写成"AI 友好"形态

把长文本切分成可独立引用的"原子段落"，逐段打分，低分段落自动改写：

**AI 友好度评分维度**（满分 100，70 分以下触发改写）：

| 维度    | 权重  | 为什么 AI 偏好             |
| ----- | --- | --------------------- |
| 数字锚点  | 35% | AI 倾向引用带具体数字、时间、统计的句子 |
| 实体锚点  | 25% | 主语+谓语+宾语完整才好"摘录"      |
| 独立可理解 | 25% | 段落不依赖上下文才能被单独引用       |
| 定义句   | 15% | "X 是 Y" 格式最易被 AI 复述   |

> ✅ **现场演示点**：粘贴一段普通文案 → 看每段的评分 → 看 AI 改写后的版本。

### 模块 ③：Schema & llms.txt 生成器

自动生成让 AI 更容易理解你站点的两类"机器可读协议"：

- **Schema.org JSON-LD**：`SoftwareApplication`、`Organization`、`FAQPage`、`Article` 等
- **llms.txt**：2024 年 Answer.AI 提出的、专给 AI 爬虫的协议（类似 robots.txt，但给 LLM 用）

> ✅ **现场演示点**：填一个产品信息 → 一键生成 JSON-LD 和 llms.txt。

### 模块 ④：知识图谱（Knowledge Graph）

用 LLM 从内容中抽取实体与关系（"产品 A 包含功能 B"），构建品牌知识图谱，支持 JSON / RDF 导出。

## 三、技术深度：不是 PPT 项目，是工程化实现

### 3.1 技术栈

| 层级   | 选型                      | 为什么选它                |
| ---- | ----------------------- | -------------------- |
| 后端   | Fastify + tRPC          | 端到端类型安全，前后端共享类型      |
| 前端   | Vue 3 + Naive UI + Vite | 轻量、上手快、生态成熟          |
| 数据库  | PostgreSQL + pgvector   | 关系数据 + 向量相似度一体存储     |
| 向量检索 | Zvec（进程内）               | 免运维、低延迟，避免引入独立向量库    |
| 任务队列 | pg-boss                 | 基于 Postgres，无额外中间件依赖 |
| LLM  | OpenAI 兼容协议             | 一套适配器兼容智谱 GLM、通义千问等  |

### 3.2 工程质量数据

| 指标         | 数值                     |
| ---------- | ---------------------- |
| 源码行数（不含测试） | \~4,900 行 TypeScript   |
| 测试文件数      | **48 个**               |
| 平台适配器      | **8 个**（每个都有独立测试）      |
| 代码模块       | 6 个核心模块 + 4 个 core 子系统 |
| 测试框架       | Vitest（TDD 开发）         |

**关键工程亮点**：

- **每个平台适配器都做了独立单测**（如 `deepseek.test.ts`、`perplexity.test.ts`），保证平台 API 差异被正确处理。
- **竞品匹配做了三级引擎**：精确匹配 → fuzzy 模糊匹配（fuzzysort）→ domain 域名匹配，应对 AI 答案里品牌名千变万化的写法。
- **向量检索用于查询聚类和实体消歧**，避免重复监测、重复入库。
- **多租户架构**：Workspace 隔离，每个租户的平台凭证独立加密存储。

### 3.3 系统架构图

```
查询库 → 平台适配器 → AI平台API → 结果分析 → 引用事件入库 → Dashboard
                                                              ↓
内容页面 → 原子化 → 评分 → 低分段落改写 → 任务审核 → 发布 → 重新生成Schema
                                                              ↓
                  监测 → 优化建议 → 发布 → 监测效果变化（闭环）
```

## 四、AI 协作开发：本项目就是用 TRAE + AI 工具链构建的

**这条卖点有据可查**——仓库里同时配置了 **4 套 AI 编程工具**，全部带完整 skills/rules：

| AI 工具    | 配置目录         | 文件数  | 作用                                 |
| -------- | ------------ | ---- | ---------------------------------- |
| **TRAE** | `.trae/`     | 61   | superpowers-zh 框架、25 个 skills、规则文件 |
| Codex    | `.codex/`    | 60   | 代码 review、TDD                      |
| Qwen     | `.qwen/`     | 60   | Vue3/Naive 脚手架、质量门禁                |
| OpenCode | `.opencode/` | 3494 | 多 agent 协作                         |

### 4.1 用 TRAE 做了什么

- **TDD 开发流程**：每个模块先写 spec（`docs/superpowers/specs/`）→ 写测试 → 写实现 → 验证。git log 完整记录了这个流程：
  ```
  docs: 新增国外平台适配+竞品模糊匹配设计 spec      ← 先写设计
  feat(adapter): 新增 Perplexity 平台适配器          ← 再写实现
  feat(adapter): 新增 ChatGPT Search 平台适配器
  feat(adapter): 新增 Gemini 平台适配器
  refactor(monitor): competitors 类型升级            ← 持续重构
  ```
- **superpowers-zh 技能框架**：加载了 brainstorming、test-driven-development、systematic-debugging、writing-plans 等 20+ skills，把"需求分析 → 设计 → TDD → 验证"的全流程结构化。
- **dispatching-parallel-agents**：多个平台适配器并行开发，每个独立测试。

### 4.2 AI 协作带来的效率提升

- **单人完成了一个本应 3-4 人团队的工作量**：前端控制台 + 后端 API + 8 个平台适配器 + 4 大业务模块。
- **测试覆盖率高**：48 个测试文件，AI 协助按 TDD 流程产出，不是事后补测试。
- **从 spec 到代码可追溯**：每个功能都有对应的设计文档（`docs/superpowers/specs/`），AI 按 spec 实现，人审通过。

> 💡 **这正是 TRAE Friends 的精神**：用 AI 把一个人的创造力放大成一个团队的产出。GeoCiteOps 本身就是这个理念的产品级证明。
